Preface

What This Is, and Is Not

This is a companion to the mid-project manual (v1/v2) already circulating for this project, not a replacement for it. That document was written checking the live site and prior audit chapters; this one was written with the actual repository cloned, its branches diffed, its migrations read line by line, and one real merge (arty/exam-ui into main) carried out during the audit itself. Where the two documents overlap, this one notes it and gives the more current or more directly verified figure. Where they don't overlap, this one is additive.

Every claim here is tagged Verified in code, Verified live, or Unverified — the same discipline the mid-project manual's Agent Rules ask for (its AR7). The Decision Register's ruling column is intentionally left blank throughout; filling it is the one thing this document does not do.

Part II · Drift

Doctrine Drift — Where the Written Record and the Shipped Code Disagree

II.1 Faculty scope: written brief versus seeded content

PROJECT_BRIEF.md names the seven starting faculties as Medicine, Pharmacy, Biochemistry, Microbiology, Law, Economics, and Insurance. What is actually seeded with real departments and courses, across migrations 0007, 0008, 0011, and 0013, is Medicine, Pharmacy, Nursing, all Engineering disciplines, Law, General Studies (GST/GSS), and Environmental Management & Toxicology. Four of the seven originally named faculties — Biochemistry, Microbiology, Economics, Insurance — have zero seeded content. Four faculties never named in the brief do.

Verified in code — confirmed by reading PROJECT_BRIEF.md against migrations 0007/0008/0011/0013 directly.

Was this pivot a real founder decision made in a conversation that never made it back into PROJECT_BRIEF.md, or did it drift unintentionally across several agent sessions each adding whichever faculty seemed reasonable at the time? Either way — is the seven-faculty list in PROJECT_BRIEF.md now wrong and due for a rewrite, or is the seeded content the thing that's wrong and due for correction back toward the original seven?

II.2 A broken append-only log

DECISIONS.md states its own rule plainly: "Never edit a past entry." Its most recent entry (2026-09-13, "Onboarding-flow merge EXECUTED") opens with "Status update to the 2026-09-12 19:57 UTC entry above" — but no entry dated 2026-09-12 exists anywhere in the file. Either an entry was deleted, breaking the file's own stated rule, or it was referenced before ever being written.

Verified in code — read the full file; the referenced entry is absent.

Do you have the missing entry's content anywhere else (an earlier chat, a draft), so it can be restored rather than left as a permanent gap in the record? If it's truly lost, should the current entry be amended (an exception to "never edit," logged as such) to remove the dangling reference, or left exactly as-is so the gap itself is part of the honest record?

II.3 Two "reused taxonomy engine" claims, not yet cross-checked against each other

DECISIONS.md and INVARIANTS.md both state the taxonomy is reused from grantapp-shell's exact two-axis baseline. Having audited grantapp-shell directly this same session: its actual live taxonomy (per its own TAXONOMY.md) is Cognitive Patterns (Pragmatic, Logical, Canon/Administrative, Statistical/Predictive, Pure Mathematical) and Information Types (Essential/ Definitive, Contextual/Historical, Abstract/Visual, Supply Chain/Procedural, Mathematical Proofs). The values seeded into CGPA's taxonomy_tags (migration 0003) match this. Verified in code, cross-repo — no drift found here, stated for completeness since it was an explicit claim worth checking rather than assuming true.

Part III · Content

Content & Data Integrity

III.1 The keystone bank has zero real, approved content — not "56 of 76 pending, 20 fine"

The mid-project manual's risk K2 states 56 of 76 keystone_questions are pending. That figure is accurate as a row count, but its framing implies the other 20 are legitimate approved content offsetting the backlog. They are not: all 20 are BCH101 (Biochemistry) rows explicitly marked [TEST FIXTURE], generic placeholder options, committed with an inline comment stating they exist purely so the adaptive-selection algorithm has data to weight against during development, and "should never be mistaken for authored curriculum material." The real count of approved, real-content keystone questions in the schema right now is zero.

Verified in code — read migration 20260912184327_cgpa_dev_seed_test_questions.sql in full.

Should the 20 test-fixture rows be deleted from the seed migration once real BCH101 content exists (if Biochemistry re-enters scope per II.1), or left in permanently as fixture data clearly separated from production content by a flag the application layer checks?

III.2 GST101 duplicated across two departments

Migration 0005 seeds GST101 ("Use of English") under the computer-science department. Migration 0008 separately seeds GST101 ("Use of English and Communication Skills I") under general-studies. No uniqueness constraint on (department_id, code) or normalized-name matching exists to have prevented this.

Verified in code.

Merge these two rows into one (which department should own it — GST courses conceptually belong to General Studies, not Computer Science), or add a uniqueness constraint now so this specific class of duplicate can't recur as more departments get seeded independently by different agents?

III.3 No admin surface exists for any of this

There is no route anywhere in src/routes resembling an admin panel. my-submissions shows a student their own submission status, read-only — that is the only place approval_status surfaces in the UI at all. Moving a keystone question from pending to approved, or merging the GST101 duplicate, currently requires a direct SQL edit against the live database.

Verified in code — find src/routes -iname "*admin*" returns nothing.

 ? Part III Question

Given zero real approved content exists and there's no way to approve any without raw SQL, is a minimal admin approval screen (even a single unstyled page: list pending, approve/reject button, done) the actual highest-priority next build item over anything else in this document?

Part V · Operations

Pipeline & Operations

V.1 No CI/CD pipeline exists

No .github directory anywhere in the repo. Nothing runs on push or on pull request — no build check, no type check. grantapp-shell (the sibling UTME product) has one, and its build was found broken and fixed this same session; this repo has no equivalent to break yet, but also nothing to catch a break when it happens.

Verified in code.

V.2 Dev-auth-bypass, well-built but worth a live confirmation

CGPA_DEV_BYPASS_AUTH is real and well-gated in code — never defaulted true, clearly documented, resolves every request to one fixed test student when enabled. Its risk is entirely operational: whether it is set true in the actual Vercel production environment variables, which is outside what a code audit can see.

Unverified — requires checking the live deployment's environment variables directly.

V.3 Offline requirement: confirmed as doctrine, absent in code

EXPERIENCE_CONTEXT.md #5 states the app is used heavily offline and calls this a data/infrastructure requirement, "not yet built — no service worker, cache strategy, or local-first data layer exists in the repo as of this doctrine's writing." That remains true after this audit; nothing in the merged arty/exam-ui work touched offline capability.

Verified in code — confirmed still absent post-merge.

 ? Part V Question

Of the three items above, which is the actual next build priority — CI, confirming the dev-bypass flag's production state, or starting the offline layer — given that all three have sat unaddressed through several sessions of feature work?
