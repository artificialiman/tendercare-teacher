Preface

What This Is, and Isn't

This manual exists because a specific complaint — "the staff auth/role and therefore the September 1 refresh is very broken" — turned out, on direct investigation, to be three distinct bugs stacked on top of a fourth, unrelated gap (the admin routes had no auth guard at all). None of those four were visible from the outside. Each was found by reading actual files and actual git history, not by trusting an earlier session's summary or this system's own memory of itself. That is the method this document tries to keep applying past the one bug that prompted it.

Every factual claim below carries an evidence grade:

verified‑in‑codeRead directly from a migration, route file, or component in a fresh clone, this session.
verified‑liveConfirmed against the running Supabase project, not just its schema files.
unverifiedStated by someone, in a commit message or an earlier session, but not independently confirmed here.

This is not a build plan. Every option offered in the Decision Register is a placeholder for you to strike through, not a recommendation ranked first. Where this manual states a default, it states it because a register row cannot be left with a blank options column — not because the default is believed correct.

Part II · Glossary & Doctrine

Terms This Manual Uses, and the Ones It Can't Yet Define

GrantApp UTME (a separate product, same GitHub account) runs on an explicit, written doctrine — Antifailure, Antitheft, Antisweat — with a ranked priority order for when they conflict. Nothing equivalent has been found for Tendercare in any session this manual draws on. The iman-doctrine repo's BUILD-DOCTRINE.md exists and is meant to be localized per project, but no session has confirmed it was ever localized for Tendercare specifically.

Terms used informally throughout this manual, borrowed from that other product for lack of a Tendercare-specific vocabulary:

  • Antifailure — a degraded, visible failure state is acceptable; a silent or corrupted one is not.
  • Antitheft — protecting the thing of value (here: exam integrity, student data, result authenticity) from being taken or falsified.
  • Antisweat — not building more than the current stage needs.

Whether these are the right three terms for a school records system, rather than an exam-prep platform, has not been asked before now.

Part II Question

Is there a written doctrine for Tendercare that this manual simply hasn't been pointed at — and if not, should localizing BUILD-DOCTRINE.md for this project be the actual next artefact, ahead of any more feature code, the same way a proscale doctrine was the blocking question for the CGPA manual?

Part III · The Three Surfaces

What Each Repo Actually Does, Chapter by Chapter

Chapter 1 · tendercare‑web

Fully static until a recent commit added one real Supabase client, used specifically to read the feed. Everything else — yearbook, alumni, about, sports — is prerendered from either hand-authored markup or a generated JSON file committed to the repo (alumni.json, and now yearbook.json).

1.1 · The yearbook is no longer hand-authored, but it isn't populated either

The old /yearbook page was ~40 individually hand-written student cards for the Class of 2025 — real names, real quotes, no template underneath. A genuinely data-driven replacement now exists, reading a new yearbook.json and a generator script (scripts/generate_yearbook_json.py) that pulls the current SS2/JSS2 cohort from Supabase by stage/level, never by a hardcoded class id. verified‑in‑code

That script has never actually been run against live data — no session so far has had both the Supabase credentials and the reason to run it at the same time. The shipped yearbook.json is honestly empty, with a note saying so, mirroring how alumni.json handled the same situation before the Alumni Almanac had real graduates to show.

1.2 · Portrait provision is two-thirds done

Invariant #13 names three places a student's portrait_url should surface: the yearbook (done, above), the result roster, and the login gate. The last two were deliberately not attempted — both routes lead into generate.py, the script that computes real transcripts, which felt like the wrong thing to touch without more room to verify it against real data than one session had.

Part III.1 Question

Was deferring the result-roster and login-gate portrait work the right call, or has it been sitting long enough that it should be scheduled now — and separately, who actually runs the yearbook generator, and on what trigger: manually when someone remembers, or tied to the same event that runs promotion?

Chapter 2 · tendercare‑teacher

This is where the actually-broken complaint lived, and where the most has been found.

2.1 · The auth-hook bug chain (now fixed, confirmed enabled)

Three stacked bugs, each only visible once the previous one was fixed and tested live:

  1. No Custom Access Token Hook existed at all, so auth.jwt() ->> 'role' — the check every RLS policy and RPC function assumed would work — was reading a claim that was never actually being set.
  2. The first hook migration returned the wrong shape, which made login appear to succeed while every subsequent call 401‑ed.
  3. The corrected hook then collided with a genuine PostgREST reservation: role is a name PostgREST itself uses to attempt SET ROLE, so using it as a custom claim threw a real Postgres error. The final fix renames the claim to app_role everywhere.

You have confirmed the hook is enabled and pointed at the current function version. verified‑live (by your statement). Whether every previously-active staff/admin session has done the one fresh login needed to pick up the corrected claim is not something this manual can check.

2.2 · Two role-check mechanisms now coexist, unremarked

Server-side RLS and RPC functions read auth.jwt() ->> 'app_role' — the custom claim the hook promotes. The one place a role is read client-side (src/routes/+page.svelte, and now the new authGuard.ts) reads session.user.app_metadata.role instead — a different, natively-present field that needs no hook at all and was never touched by the three-bug saga. Both currently happen to agree, because both are fed by the same app_metadata value at the source. Nothing enforces that they keep agreeing if a future change updates one path and not the other.

2.3 · The admin routes had zero guard; this session added one

Every other staff page (/attendance, /score, /roster) independently checks for a session on mount and redirects to /login if none exists — a real, if duplicated, convention. /admin, /admin/staff, and /admin/analytics had none of it: reachable by direct navigation by anyone, logged in or not, the only "protection" being that the dashboard simply didn't link there for a logged-out visitor. This is now fixed, extending the existing per-page pattern rather than introducing server-side session handling (no hooks.server.ts exists anywhere in this app, and none was added). /admin/staff's actual write actions (add, remove) are now additionally gated to app_metadata.role === 'admin', not just any staff session, matching what the RLS policy already silently enforced. verified‑in‑code

2.4 · No mutation in this app is attributed to who made it

An earlier decision, recorded as settled: real per-teacher accounts and attribution are wanted now, driven specifically by staff turnover — sacking, transfers, leave — being the most active lifecycle in the whole system. No created_by or updated_by column, or equivalent, has been found on any table this manual's audits have touched — not on score entries, not on roster edits, not on staff CRUD, not on the new bio/portrait fields. Real per-teacher login exists (the auth-hook chain above is about exactly that); attribution of what a logged-in teacher actually did does not yet appear to.

2.5 · How does anyone become admin?

No admin-promotion UI was found anywhere in this codebase. app_metadata.role appears to be set by editing a user directly in the Supabase dashboard — outside any app-level screen. That may be entirely fine at the current scale (one school, a handful of admins), but it means the actual answer to "who can become admin" currently lives in dashboard access, not in anything this app displays or governs.

Part III.2 Question

Of the three items above that aren't bugs exactly but aren't settled design either — the two role-check paths, missing attribution, and dashboard-only admin promotion — which deserve a ruling now, and which are fine to leave as they are at this school's current size?

Chapter 3 · tendercare‑portal, and the pipeline behind it

The smallest of the three repos, and arguably carrying the largest operational risk right now.

3.1 · Twelve demo students, and September 1 has already passed

scripts/report-pipeline/students/ in tendercare‑teacher — the source generate.py actually reads to produce the JSON files tendercare‑portal serves — contains twelve demonstration files. The real, currently-enrolled student body is not in this pipeline. This is explicitly a data problem, not a code problem — the generation mechanism itself is built and works — but it means that today, no real student could actually check a real result, regardless of how correct the auth fix or the admin section now are.

3.2 · The distribution mechanism is yours, by design, and its status is unknown to this manual

Result-checker codes — one per student per term, the revenue mechanism, distributed manually over WhatsApp — were explicitly kept out of agent scope. The UI carries a disabled placeholder tile and nothing else. Whether the actual generation/distribution tool is ready, in progress, or not yet started is not something any session behind this manual has visibility into.

Part III.3 Question

What's the real plan and timeline for getting the current student body's data into the report pipeline — and does the auth/admin work this manual documents actually unblock that, or was it always a separate, parallel track that this manual has no visibility into?

Manual-Level Closing Questions

Not Chapter-Scoped — the Ones That Shape Everything Above

These are the questions I believe actually determine the shape of the rest of the register, rather than let the manual trail off into detail.

First

Is the real, current blocker to "the September 1 refresh works" actually auth anymore — now that the hook chain is fixed and the admin gap is closed — or was auth always downstream of the bigger blocker, which is that the report pipeline still has twelve demo students and the real class of 2026/2027 isn't in it yet (D11)? If the second is true, everything in Parts II, VI, and VIII above is real but not urgent, and D11/D12 are the only two rows that actually matter this week.

Second

Attribution (D06) was already decided once — "wanted now, driven by staff turnover" — and appears not to have been built. Is that a genuine gap this manual just found, or is there attribution logic somewhere none of the sessions behind this manual have looked, and the real issue is that nobody's checked?

Third — and I think most important

This manual was written the same way the reference one that prompted it was: by re-reading actual files rather than trusting what earlier sessions said about them, specifically because the original complaint ("very broken") turned out to trace through three real bugs that had each been silently accumulating. Do you want every future session on these three repos to open the same way — read this manual and the Decision Register before writing code — and if so, should that be a standing instruction written down at the repository root, the way INVARIANTS.md already is, rather than something true only because it was discussed in one conversation?
