Preface

What This Document Is and Is Not

This is not a pitch document. It does not exist to make the project sound finished, ambitious, or impressive. It exists because five prior chapters of plain-prose auditing — reading actual files, actual live row counts, actual git history, rather than trusting memory or intention — surfaced a real, recurring pattern: things I built, or things other agents built, that were reasonable engineering decisions made under time pressure or incomplete specification, sitting silently in the codebase as if they were settled architecture, when in fact almost none of them had ever been explicitly confirmed as your decision rather than an agent's guess.

This manual continues that discipline, but reorganizes it. Where the five chapters were organized by subsystem (routing, database, question flow, infrastructure, deployment futures), this manual is organized as a startup manual — the document a founder hands to an engineer on day one of the “we've proven the prototype works, now we build it properly” phase. It assumes UI, Device Identity (the anti-theft device-binding system), and Data Infrastructure (the cgpa schema, RLS posture, auth wiring) are already designed and have already proven themselves to work — which, per the prior chapters' verified findings, is true in the narrow sense that the code exists, type-checks, and builds cleanly, and is not yet fully true in the stronger sense of having been exercised by real students at scale, since Chapter Three's live row counts showed most of the actual data tables sitting empty in production as of the time I checked them.

Every paragraph below ends with at least one question. Every chapter ends with a chapter-level question. The manual itself ends with a set of questions that only you can answer, because they are about what you want the brand to be, not about what the code currently does. I am not going to answer these questions for you by guessing plausibly and moving on — that is precisely the failure mode this whole exercise exists to prevent.

Chapter One

The Three-Stage Native Roadmap, Stated as an Actual Sequence, Not an Aspiration

You've now specified something I did not have before this conversation: a concrete, ordered, three-stage plan — one vanilla build, one SvelteKit build, one fully native build — with the SvelteKit-based Progressive Web App representing “the pinnacle of anti-theft” before the native rewrite begins, and the database migration to CGPA's own Supabase project happening immediately after the PWA stage is live, not concurrently with it and not deferred indefinitely. I want to restate this precisely so I can be corrected if I've misread the sequencing: Stage 1 is a vanilla (I read this as: not SvelteKit, likely plain HTML/CSS/JS or a minimal framework) implementation; Stage 2 is the current SvelteKit codebase, hardened specifically for anti-theft as its defining achievement; Stage 3 is native — and only after Stage 2 is genuinely live does the database split happen, followed by the native rewrite.

This reframes something I treated as symmetric in Chapter Six's “Part Two” as actually sequential and dependency-ordered, which changes the engineering calculus meaningfully. If the native rewrite is Stage 3, definitionally after the database split, then Chapter Six's Section 7 point — that doing the database migration as a clean break (Option A, new Auth, new project) gives a native/offline rewrite a better foundation to build against — stops being a nice-to-have observation and becomes load-bearing sequencing logic: the database has to be independent before Stage 3 can begin cleanly, because Stage 3 is not “wrap the existing thing,” it's a genuine rewrite, and a genuine rewrite against a shared, UTME-entangled Supabase project would import Chapter Five's shared-fate risk directly into the one part of this roadmap meant to be the most independent and most carefully built.

Is my reading of the sequence correct — vanilla, then SvelteKit-as-PWA, then native, with the database split sitting between stage two and stage three rather than at the very start or the very end? And is “vanilla” here a completed or planned stage — does a vanilla-JS version of this product already exist somewhere I have not been shown, or is it a planned first stage that the SvelteKit build was meant to supersede, in which case is the SvelteKit codebase I've been auditing across five chapters actually Stage 2, already underway, rather than a standalone deliverable?

1.1 What “the pinnacle of anti-theft” as a PWA-stage goal actually implies for the current codebase

I want to take this phrase seriously as a specification, not a slogan, because it changes what “done” means for the SvelteKit stage in a way that isn't yet reflected in the current code. Chapter Two's audit of +layout.svelte and Chapter Three's audit of cgpa.devices both described a real, working 2-device self-serve limit — hashed fingerprint (user-agent plus a localStorage-persisted random ID), checked at login and signup, with a self-serve removal screen for when the cap is hit. That is a real anti-theft mechanism, and it is meaningfully different from, and I'd argue currently weaker than, UTME's own device-binding approach, which — as I documented while building UTME's own admin tooling in a separate session — is a hard, 1-device lock requiring either self-serve removal or (for certain exempt accounts) admin intervention, not a 2-device allowance.

If the PWA stage is meant to be “the pinnacle of anti-theft,” full stop, before any native rewrite, I do not currently know whether that means: tightening CGPA's device limit to match or exceed UTME's 1-device rigor; adding server-side heuristics beyond device fingerprinting (IP-based anomaly detection, session-concurrency limits, something else entirely); building anti-theft protections around the content itself (question-bank scraping prevention, rate-limiting on quick-test-session calls, watermarking) rather than only around account sharing; or something I haven't considered because it wasn't in scope for the audit chapters. What does “pinnacle of anti-theft” concretely mean beyond the device-limit mechanism that already exists — is the 2-device model itself the target state, just needing to be verified as robust under real adversarial use, or is there a harder anti-theft ceiling you have in mind that the current codebase doesn't yet reach?

1.2 The vanilla-to-SvelteKit-to-native pattern as a hedge against framework lock-in, and whether that reading is correct

One plausible reading of “one vanilla, one SvelteKitted, one native” is that it functions as a deliberate hedge: prove the product concept works with the least framework commitment possible (vanilla), prove it can scale and be secured properly with a real framework's conveniences (SvelteKit), then commit to the heaviest, most permanent investment (native) only once both prior stages have de-risked the product and the security model. Under this reading, the reason SvelteKit is a middle stage and not the final one isn't primarily about offline capability (Chapter Six's framing) — it's about not fully committing to any one technology stack until the product itself is proven, with SvelteKit specifically chosen for stage two because it offers server-side rendering and a mature ecosystem without the platform-specific lock-in of jumping straight to native.

Is this the actual reasoning behind the three-stage structure, or is the SvelteKit-to-native transition primarily about the offline/local-data-ownership requirement from Chapter Six's Part Two, with the framework-hedging benefit being incidental rather than the point? This matters because it changes what “prove SvelteKit works” should be optimized for during this stage — proving the framework choice was sound and scalable, versus proving the anti-theft/security model specifically, versus proving the product concept has real user demand before native investment is justified.

Chapter Two

Database Independence as a Precondition, Not a Parallel Track

2.1 Restating Chapter Six's options under the new, sequenced understanding

Chapter Six laid out three options for the database split — clean-break new Auth (Option A), shared-auth-split-data (Option B), and defer (Option C) — as if they were live alternatives with roughly comparable merit depending on risk tolerance. Under this manual's new information, Option C (defer) reads very differently: if the database split is a hard precondition for a well-founded native Stage 3, deferring it doesn't just accept Chapter Five's shared-infrastructure risk a little longer — it defers the start of Stage 3 by the same amount, since Stage 3 depends on it. Option B (shared auth, split data) also reads worse under this framing than it did in Chapter Six, because it explicitly does not give the native stage the clean, fully-independent foundation the manual's stated goal implies is wanted. That leaves Option A — full clean break, CGPA gets its own Supabase Auth, all 12 current accounts re-register — looking like the option that actually matches the roadmap you've described, not merely one of three defensible choices.

Do you want me to treat Option A as the settled direction now, and start planning concretely for a full clean-break migration timed to happen right after the PWA stage is confirmed live — including the real, user-facing cost named in Chapter Six, that every current CGPA account holder re-registers from scratch — or is there a reason to keep the shared-auth question genuinely open a while longer, for instance if the number of real accounts is expected to grow substantially during the remainder of the PWA stage, making a later clean break costlier than doing a shared-auth split sooner?

2.2 What “gets its own Supabase account and project” implies about billing, ownership, and operational independence that a schema-level split alone doesn't address

Chapter Six's Part One focused on the technical shape of the migration — which tables move, what happens to auth, foreign keys across servers. It did not address something your phrasing here makes newly relevant: “its own Supabase account,” not merely its own project. A new project under the same Supabase organization/account is a smaller, cheaper, more mechanically contained change than a genuinely separate Supabase account — separate billing, separate organization-level settings, separate API key management, potentially separate team access if other agents or collaborators need scoped permissions to one product but not the other.

Is “its own Supabase account” meant literally — a fully separate Supabase organization, with its own billing relationship, independent of whatever account currently hosts the shared UTME/CGPA project — or is “account” being used loosely here to mean “project,” matching Chapter Six's schema-and-tables-level framing? This has real, practical consequences for who needs login credentials to what, and whether CGPA's infrastructure becomes something you or a specific team member owns and controls independently of UTME's infrastructure ownership, which is a business and access-control question as much as a technical one.

3.2 The one place scale and anti-theft doctrine directly collide, which needs an explicit ruling

I want to flag a genuine tension rather than let it sit unnoticed: anti-theft's device-fingerprinting and account-sharing prevention, taken to its logical extreme, tends to work against frictionless scale — every additional check, every additional server round-trip to verify a device or session, every additional constraint on how freely a student can move between devices, is a small tax against the smoothest possible growth experience. UTME's stricter 1-device model is, by construction, more anti-theft-rigorous and more scale-friction-inducing than CGPA's current 2-device allowance. If Stage Two's explicit goal is to be “the pinnacle of anti-theft,” and proscale doctrine (whatever it turns out to specify) pulls toward minimizing friction, which doctrine wins when they conflict, and is there a principled way to state the priority order rather than resolving it ad hoc, case by case, as specific features get built?

Chapter Five

What Changes About Every Prior Chapter's Findings, Once the Native/Offline Endpoint Is Treated as Certain Rather Than Speculative

Chapter Six of the original audit treated native/offline as a possible future, weighed against alternatives. This manual establishes it as a committed Stage 3. I want to revisit a handful of the audit's earlier findings specifically through that lens, because “this will definitely become native and offline” changes whether certain current patterns are acceptable technical debt or genuine architecture-level mistakes that will cost more the longer they're left uncorrected.

5.1 The /analytics all-time, unpaginated, unfiltered query, reconsidered

Chapter Four's audit of /analytics noted the mastery query fetches a student's entire history with no date filtering, no pagination, no limit. At current scale (Chapter Three: mastery_state sitting at zero rows in production) this is a complete non-issue. Under a native, offline-capable rewrite, this exact query pattern — “fetch everything, render it all” — is close to the opposite of how an offline-first client should think about data: a local-first architecture typically wants incrementally-synced, bounded datasets, not “pull the full table on every screen load,” because the whole premise of local-first is that the device holds a working copy, synced and pruned deliberately, not a live mirror of an unbounded server table.

Should the current SvelteKit/PWA stage start shaping its data-access patterns now — smaller, bounded, paginated queries; explicit “what does the device need to know locally” thinking — specifically to make the eventual native rewrite's data layer less of a from-scratch redesign, even though nothing about the current scale requires this optimization today? This is a real tradeoff: it would mean writing more careful, more constrained code during the PWA stage for a benefit that only pays off at Stage 3, at the cost of slower feature velocity now.

5.2 The three-copy-pasted-upserts pattern (Chapter Five, Section 3), reconsidered as a native-rewrite liability

Chapter Five named the repeated “ensure a students row exists” upsert as glue that outlived its own justification once the handle_new_user trigger existed to make it redundant. Under a near-certain native rewrite, every one of these patterns is code that either gets ported faithfully (carrying the redundancy forward into a second codebase) or gets cleaned up now, once, in the version that's easier to still edit.

Do you want a dedicated cleanup pass — removing now-redundant defensive code, consolidating repeated patterns into shared functions, generally tightening the SvelteKit codebase — scheduled explicitly before the native rewrite begins, treating the PWA stage's final form as “the reference implementation Stage 3 gets built from,” or is the expectation that Stage 3 is a large enough rewrite anyway that current-codebase tidiness won't meaningfully affect it, since most of it won't be directly ported code regardless?

5.3 What “native” resolves that a WebView wrapper (Chapter Six, Section 5) does not, now that native is the stated final stage rather than one option among several

Chapter Six laid out WebView-wrapper, WebView-plus-offline-layer, and full-native-rewrite as a spectrum, without knowing a genuine native endpoint was already decided. With that now established, I want to ask directly rather than assume: is “native” here meant in the strictest sense — real Kotlin/Swift/platform-specific UI, no WebView anywhere in the final product — or does “native app” in your usage include a WebView-wrapped app with a genuine local-first offline data layer underneath it, which produces an installable, app-store-distributable, offline-capable product without necessarily rewriting every UI screen in platform-native code? This is not a pedantic distinction — it's close to the single largest cost variable in the entire roadmap, and Chapter Six's spectrum showed these two things can look similar from a user's perspective (an icon on their home screen, works offline) while being wildly different engineering efforts underneath.

 ? Chapter Five Question

Given that Stage 3 is now a certainty rather than a possibility, should any part of the current SvelteKit build be deliberately architected as shared, reusable business logic — the scoring functions, the mastery-update formula, the course-selection algorithm — written in a way that could be extracted and reused by a native client later (for instance, as a well-isolated TypeScript library with no SvelteKit-specific dependencies), rather than left embedded inside SvelteKit route handlers the way lib/quiz/mastery.ts currently is — mostly separable, per Chapter Five's own praise of it, but still written assuming a SvelteKit/Supabase server context around it?

v2 scope note on Chapter Five

With native outside the active path, sections 5.1 and 5.2 still apply, re-grounded: bounded queries and a cleanup pass serve a frozen reference implementation (Part V, Stage 3) and PWA performance, not a later rewrite. Section 5.3 (strict native versus WebView) is settled by scope (D21). The extraction question at the end of the chapter (D22) stays open, since an isolated scoring and mastery module benefits a PWA regardless.
